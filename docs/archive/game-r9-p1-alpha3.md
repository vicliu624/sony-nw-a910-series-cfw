# R9 P1 / 双状态图标 ALPHA3：原厂系统调用接口修正

用户实机反馈：ALPHA2已安装，USB完全拔除后按RESET仍直接进入Walkman，没有选择页。
此前只用插线跳过逻辑解释不充分。ALPHA3针对已经复现的底层不兼容修正，仍需用户复测。
没有自动安装；不宣称实机已修好或绝对不会卡死。

## 已确认的原因

从原1.03内核中恢复符号后，原vector_swi位于0xc0022ae0。
ARM模式下它在0xc0022b0c读取触发SWI的指令，0xc0022b30取立即数，
0xc0022b34异或0x900000得到系统调用号；并不按新EABI习惯直接使用r7。
原libc-2.3.3.so也使用svc 0x900005等旧接口调用open。

旧a918-boot在ARM模式下把42放进r7并执行svc 0，期望pipe；在这个真实内核中
却跳到了arm_syscall(0xc0028388)，没有进入sys_pipe。因此旧QEMU用户态通过
不能证明原设备兼容：当时的系统调用替身/环境接受了r7+svc0，没有覆盖原内核入口。

ALPHA3用独立ARM汇编桥，把C调用的系统调用号编码为SWI 0x900000+nr。
例如首个pipe变为svc 0x90002a，原内核实际分派到sys_pipe(0xc0026e84)。
信号返回也改成svc 0x9000ad，补测了SIGTERM处理及返回。
C程序仍使用AAPCS编译；没有仅修改ELF版本标志冒充兼容，也没有更换内核。

## 对照证据

scripts/check-sony-kernel-syscall-abi.py复用原内核ARM指令，跳过与分派无关的
CP15控制寄存器写入，并在抵达系统调用函数时停下，不执行真实硬件操作。
22组对比覆盖使用的关键调用号：旧svc0均未进入相应入口，旧式SWI则正确分派。
还分别执行旧/新实际ELF到首个SVC，取得指令后送入原内核解码器比较。

旧程序SHA256：0e416d2ea0877f524d10df3aca6267f6512f6c0ef22c6326d51c70f742cb5f6e。
实际报告随包original-kernel-ABI-test.json提供，绑定新程序SHA256。

同时通过P1真实ROM设时/孵化/喂食/存档自测、200次Tetris新局、ARM926运行、
正常/异常/停滞/SIGTERM监护、18个ARM硬件接口模拟用例、9个挂载脚本用例、
6个打包后启动脚本用例，以及Rockbox独立解包和全文件比较。
这些补齐系统调用层证据，仍不等于完整A918设备、QFB显示/USB/存档实测。

## 复测步骤

完整解压本目录ZIP，用同目录原Sony FWUpdater.exe升级，保持所有配套文件。
不要把它与旧版UPG混在一起。版本仍1.03，没有绕过更新器检查。
等更新器确认完成，再安全断开USB。拔线后按RESET，观察WALKMAN / GAMES选择页。
默认8秒继续播放器，及时按下方向键选GAMES，中间键确认。
若仍没有出现选择页，记录是否额外停留约8秒；本次修复已证实的调用接口问题，
不以此保证设备没有其他初始化或显示问题。
